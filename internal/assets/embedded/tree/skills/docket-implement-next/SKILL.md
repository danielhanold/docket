# docket-implement-next — the implementer (autonomous)

## Overview

`docket-implement-next` runs with **no human interaction**: it picks the next build-ready change from the docket backlog and drives it all the way to an open PR, then stops at the PR handoff. One invocation handles one change — select, claim, reconcile, plan, build, review, PR, stop.

## When to use

- You want the backlog drained autonomously — pick the highest-priority build-ready change and ship it to a PR without human steering, or hand it an id set (`90,92,94`) to scope the run to those changes. A **single explicit id** is a **named invocation**: it skips the maintenance preflight and goes straight to that change's own checks (Step 0, *Named invocation*).
- Do NOT use if you want to interact during brainstorm or design — that is `docket-new-change`'s job. This skill re-brainstorms nothing; the escape hatch for a fundamentally invalidated design is to STOP and hand back to the human.

## Convention (load first — blocking)

Before anything else in this skill, invoke the `docket-convention` skill via the Skill tool — unless it was already invoked earlier in this session and its content is in context. Everything below uses its vocabulary (build-ready, metadata working tree, close-out, the `DOCKET`/`LIVE` bootstrap probes, …) without redefinition; no step below is executable without the convention loaded.

## Procedure

### Step 0 — Sync & sweep

Run the convention's **startup check** (load the convention; run the capability bootstrap; run the `repository.prepare` operation with `--repo-dir <dir> --json` as its own Bash call; validate the protocol-v1 envelope and carry its typed context values forward as literals; act on the disposition). All bookkeeping in this skill (claim, reconcile, `status`, `pr:`, `plan:`, `adrs:`, the plan and results files, build evidence) lands in the metadata worktree (`metadata_worktree_path` in the `repository.prepare` context) on the metadata branch, pushed to the metadata remote (`metadata_remote`) immediately; only the spec copy and the code land on the feature branch.

**Named invocation — no maintenance preflight.** When this run was invoked with exactly **one explicit change id** — an initial named call, an attributed retry carrying the id, or a named resume of an in-progress change — skip the implementation preflight and Step 1's status-digest certification entirely: after the `repository.prepare` operation succeeds, go **directly** to the authoritative `context.implementation` operation with `--id <id>` and the existing claim/resume path. The named path never runs `maintenance.preflight` or any maintenance sweep first — another change's failing closeout or cleanup can never halt this change before its own claim/gate; anyone who wants those maintenance outcomes runs the explicit `maintenance.preflight` or `maintenance.sweep` operation deliberately, where every problem stays visible. Every local check for the named change is kept — readiness, record revision, dependencies, effective base, claim eligibility, run context, and resume/cancellation; an `in-progress` id is served only to its own resume (Step 1). A held change (`on-hold`) is built when named. So a malformed, absent, not-ready, or improperly resumed id returns its existing typed refusal, reported with its reason exactly as a scoped-id skip is (ending `drained` when nothing else is in scope); a named request **never falls back to selecting another change**, and shared repository/configuration/transport failures keep the `halted` posture.

**The named change's own merged dependencies.** Skipping the sweep never declares a dependency satisfied. When the named path's `context.implementation` read refuses `not-ready-waiting-dependency`, **read `references/edge-paths.md` now (blocking)** for the bounded closeout of the named change's own `implemented` dependencies — never any other change's.

**Selection path only.** Otherwise — no argument, or an id set — run, before selection, the **implementation preflight** inline: resolve the `maintenance.preflight` operation from the capability catalog (never from a tool name) and run it **as its own Bash call** with `--json`. One process runs the implementation-scope sweep and the compact post-sweep read and returns one envelope; there is no child, so no completion barrier to arbitrate — a shell call that returns is terminal by construction. Validate before trusting it: `protocol_version` MUST be `1`, `operation` MUST be `maintenance.preflight`, and `sweep.scope` MUST be `implementation`; then key on exactly two fields — the envelope `result` and the Go-computed `preflight` verdict — never on prose and never on the process exit code. On `preflight: problem`, or any `result` other than `applied`/`no-op`, **halt before claiming** through the pre-claim run-reporting path, surfacing the envelope's `problem_entries` (and `reason`/`message` when the sweep or its post-sweep read failed as a whole) — before a claim there is no owned change record to write a halt on, and you never mutate an unrelated proposed record to carry it. A validation failure (wrong protocol, operation, or scope) or missing output halts the same way; no new run-tracker state exists for any of this. On `preflight: clean` with `result` `applied` or `no-op`, re-run the `repository.prepare` operation and derive readiness and claim state from fresh origin — the envelope is control-flow proof, never a substitute for metadata authority — then continue to Step 1; the envelope's `status` half (`summary`, `ready`, `findings`) is only the preflight digest, and Step 1 takes its own fresh read.

### Step 1 — Select

Build-readiness and ranking are defined by the convention's **Build-readiness & selection** section — that definition is the authority here, and this step only describes how to ACQUIRE the set it defines.

**Acquisition.** Run the `status` operation with `--json` — a write-free read; on the selection path, only AFTER Step 0's `maintenance.preflight` run and metadata re-sync (the snapshot is taken pre-sweep otherwise and would list already-merged changes). A named invocation takes no ready-queue digest — it arrives here already holding Step 0's directive to read the explicit-id bundle below. Validate the envelope before trusting it: `protocol_version` MUST be `1` and `operation` MUST be `status`. The top-level `ready` array IS the build-ready queue, already in the convention's deterministic order — final tie-break LOWEST `id`, so concurrent implementers converge on one winner. Per-change skip reasons come from each `changes[]` entry's `readiness` / `readiness_reason` fields (`readiness` vocabulary: `build-ready`, `on-hold`, `needs-grooming`, `waiting-dependency`, `stack-base-unresolved`, `not-proposed`, `auto-groom-blocked`, `invalid`; `readiness_reason` carries the human-readable phrase).

The digest is an **accelerator, not the sole channel**: the authoritative read is the `context.implementation` operation with `--id <id>` (no `--id` applies the same selection policy; an attributed retry passes the id). It loads ONE fresh snapshot and returns the change's source bytes, exact opaque **record revision**, readiness, claim-eligibility, resolved effective base, integration branch, and workflow config — the single bundle the claim and every later operation key on, so no step re-reads the change file. For the run's own `in-progress` change (a named resume) it returns the bundle with `claim_eligible: false`, the recorded branch, and a readable `halt.run_halted`; a plain named run that reads `claim_eligible: false` surfaces the refusal and ends `drained`, never claiming or building — only a resume proceeds. **Judgment on that bundle stays yours.** CONFIRM build-readiness (on the named path `on-hold` also qualifies) before claiming — a stale digest costs a re-pick, never a bad build; a typed no-candidate/absent-id/duplicate-id/not-ready/unsupported-config outcome is surfaced, never overridden. If the bundle disagrees with the digest, drop that candidate, take the next, and REPORT it; on the selection path a bundle reporting `on-hold` is dropped and reported the same way. **The exit status and the envelope's shape together govern the disposition.** A **non-zero exit**, or stdout that will not parse as a JSON envelope, **is a hard error** (config export failure, refused bootstrap guard, missing metadata worktree, failed render, or malformed output) — surface its stderr diagnostic and STOP with the **`halted`** disposition; never fall back to `active/` for a hard error, and never report `drained` for one. On **exit 0** with a valid envelope, an **empty `ready` array** (`ready: []`) means the queue is genuinely empty → `drained`. A parseable envelope that is **missing the `ready` key altogether** is malformed machine output — **reject it and STOP with `halted`**, exactly as for a hard error: the typed contract always carries `ready`, so there is no walk-`active/`-yourself degradation. Likewise a failed `protocol_version`/`operation` check.

**Scope (id allowlist).** With no argument the candidate set is the whole `ready` queue. A caller may pass an **id allowlist** of two or more ids — `docket-implement-next 90,92,94` — and selection is then **restricted to that set**, preserving the queue's order *within* it. (A **single explicit id** is not an allowlist: it is a named invocation and takes Step 0's named branch, never this filter.) The allowlist is a filter, **never a dependency override**: a scoped id that is not currently build-ready+claimable — needs-grooming, on hold, already `in-progress`, or waiting on an unmerged `depends_on` — is **skipped with its reason** (read it off that id's `changes[]` entry — a non-`proposed` `status` there is skipped for that status — or from the change file if it has none — already archived, or no such id), never force-built, and never aborts the run.

**Empty queue → `drained`.** If no candidate in scope is build-ready+claimable, build nothing and end the run with the **`drained`** disposition (see *Terminal disposition*) — the driver's stop signal.

### Step 2 — Claim (conflict-checked write)

Claim by transaction: the `change.claim` operation with `--id <id> --revision <revision>` (the exact revision from the step-1 bundle). When the dispatch prompt carried a **run context** token, pass it to the claim as --run-context <token>: the claim validates it against the started run, records durable proof binding this dispatch to its successful claim, and the parent's keyed verdict resolves ownership from that proof; an invalid or conflicting run context is a typed refusal that writes nothing — never retried as an ungated claim. A claim without the token stays supported for ungated invocations. Also pass `--selection queue` on the selection path and `--selection named` on the named path: the run tracker counts a halt toward a loop's halt limit only for a change picked from the queue. In the **metadata working tree** the operation reloads fresh origin, re-proves the change is still `proposed`, uniquely identified, build-ready, and has a resolved effective base, then applies the landed claim (`status: in-progress` + `branch: <type>/<slug>` + `updated:`) and updates the change record, `## Artifacts` block, and inline board **together in one metadata commit** on the metadata branch, pushed to the metadata remote. It returns the feature branch and a closed disposition; a wrong revision or a not-`proposed`/not-build-ready/duplicate/unresolved-base change returns `contended`/a typed refusal that **writes nothing and creates no workspace**. A lost-response retry converges by re-reading authority — an already-held matching claim returns the applied receipt or a typed `already-claimed`, a foreign claim returns `contended`; never adopt a branch or workspace as proof the claim landed. A `contended` result is the **`contended`** disposition (see *Terminal disposition*): a lost conflict-checked claim race is a normal, continue-able outcome a driver re-selects past, **never `halted`** — re-sync (re-run the `repository.prepare` operation) and re-select. No worktree yet.

**Revision lookups.** The claim pins the pre-claim bundle's revision and `change.resume-halted` the context bundle's. Before every later write to its own record — `change.reconcile`, `change.halt`, a reconcile-kill's `change.kill`, `workspace.prepare`, the revision handed to the plan-writer, the producing-change revision handed to `docket-adr`, each `change.attach-results`, and `change.mark-implemented` — the run reads the revision from the local metadata checkout in the same shell call as the write (or immediately before the dispatch carrying it): `R=$(git -C <metadata_worktree_path> rev-parse HEAD:<record path>)`, `<record path>` being the bundle's `change.path`, which does not move while the change is active. A receipt's `committed_revision` is the commit id, never a `--revision` value. On `contended`, re-sync once (the `repository.prepare` operation), look the revision up again, and retry the write once — except `change.reconcile`, which keeps its re-read-and-re-author rule (Step 3); a second `contended` follows the step's existing stop rule.

A claim of a `proposed` record that still carries a `## Run halted` section removes that section in the same transaction. **Resuming a halted in-progress change** — one the caller re-dispatches by id after a `run.verify` verdict of **`run-halted`** — goes through the `change.resume-halted` operation with `--id <id> --revision <revision> --acknowledge-quiescent`, never a fresh claim: it requires the exact marked record and the explicit `--acknowledge-quiescent` acknowledgement that the prior worker is quiescent, reprobes the branch/workspace/live gate and removes exactly the `## Run halted` marker section while preserving every other byte and checkpoint — it never resets or adopts a workspace whose writer may be live. It refuses (writing nothing) without the acknowledgement, on revision drift (`contended`), or on a live gate lock. A stranded run recovers only by the caller resuming its change by id (the `run.start` operation with `implement-next --resume <id>`), with the run tracker deciding. The claim and resume both render the inline board in their own transaction, so no separate Board pass runs here. Starting the resume also passes through the run tracker, which refuses a second run over one that has not verifiably stopped — **read `references/edge-paths.md` now (blocking)** for those run-tracker resume refusals and their remedies.

> Two agents must NOT share one local clone — each needs its own.

### Step 3 — Reconcile ⭐

Re-read the step-1 bundle's change + spec bytes against `related` + recently-archived changes, cited + recent ADRs, and CURRENT code, and decide NON-INTERACTIVELY what is true NOW (drop work done elsewhere, adjust scope, fold in new constraints). That judgment is yours; the write is a transaction. **Author** a reconcile request — structured replacement text for the owned proposal sections and still-mutable linked-spec content, the complete desired relations (`depends_on`/`stacked_on`/`related`/`adrs`/`discovered_from`) when reality requires them, and one dated `## Reconcile log` entry — and apply it with the `change.reconcile` operation with `--input <request-file>` (the request file carries `id`, the pinned `revision`, and the authored Markdown — never a shell-escaped flag). The `reconcile_log_entry` is the **section body only** — the operation writes the `### YYYY-MM-DD` heading. When nothing changed (spec, stack base, related changes, and scope all hold), send just `{id, revision, reconcile_log_entry}` with a one-line body such as "Unchanged against `<integration tip>`"; sections and relations go in only when reality requires a change. The transaction checks the exact revision and legal `in-progress` status, sets `reconciled: true`, rerenders backlinks/`## Artifacts` block/inline board, validates the whole repository, and commits atomically on the metadata branch, pushed to the metadata remote; unknown frontmatter, unlisted authored sections, line endings, and unrelated files stay byte-identical, and a request naming a non-owned field/section is a typed refusal that writes nothing. If fresh origin state diverges incompatibly, the operation returns `contended` and writes nothing — never a text-merge; re-read fresh context and re-author.

Adjacent follow-up work this pass surfaces is **noted for the final report** — nothing is minted automatically; a human captures reported work deliberately with `docket change create`, guided by the backlog verdict final consolidation attaches (Step 6.5 *Backlog match*).

Two escape hatches:

- Change now **OBSOLETE** → kill it via the convention's close-out (**read `../docket-convention/references/close-out.md` now — blocking**) — one atomic `change.kill` operation transaction that archives the record on `docket`, retargets the linked spec's back-link, and renders the inline board in its own metadata commit. Caller posture and the cleanup notes: **read `references/edge-paths.md` now (blocking)**. Because the `change.kill` operation renders the board atomically inside its own commit, **no separate Board pass follows** — the board already drops the killed change. Then return to Step 1.
- Design **FUNDAMENTALLY invalidated** (not just scope-adjustable) → STOP and escalate to the human — end the run with the **`halted`** disposition (see *Terminal disposition*), the driver's stop-and-surface signal — and **write that halt into git before stopping**: the `change.halt` operation with `--id <id> --revision <revision> --input <report-file>` records a bounded authored run-halted report into a `## Run halted` section on the in-progress change in one exact-revision transaction, leaving the branch, workspace, and evidence untouched (the authored Markdown travels as a request file, never a shell-escaped flag; a non-in-progress record is refused, writing nothing). The `report` is the section **body only** — the operation alone writes the `## Run halted` heading and dated `###` sub-heading, so the body starts with prose, a list, or a `###`-or-deeper subsection. A body carrying its own column-zero `## ` heading (a repeated or dated halt heading included) or an unterminated code fence is refused `invalid-input` (`invalid-section-markdown`, field `report`), writing nothing; keep heading examples inside closed code fences. This is the producer half of the section the convention defines: a `halted` disposition that exists only as a sentence in a completion report is exactly the untrusted self-report the `run.verify` operation was built to stop trusting. The same write is required for **any** hard error that ends the run `halted`, wherever it occurs. Any hard error that prevents reaching a PR is likewise `halted`. This skill cannot re-brainstorm alone; re-brainstorming is a human act handled by `superpowers:brainstorming` + `docket-new-change`.

### Step 4 — Worktree + plan

Step 3's `applied` reconcile receipt proves its exact-lease push landed on the metadata branch. Prepare the owned feature workspace:

```
workspace.prepare  --id <id> --revision <revision>   # resolve argv from the capability catalog
```

The `workspace.prepare` operation reloads the authoritative snapshot, resolves the effective base through the landed domain policy (the app adds NO base or stack policy of its own), constructs the workspace target, and returns the canonical owned workspace path, exact base commit, feature ref, and disposition. It requires the change to be `in-progress` at that exact `--revision` (a losing claimant creates no workspace); a `contended`/`unknown` disposition passes through verbatim, never a force. For a change carrying `stacked_on:`, the resolved base is the parent's effective base, not `origin/<integration_branch>`, and the step-7 PR targets it; **read [`../docket-convention/references/stacked-changes.md`](../docket-convention/references/stacked-changes.md) now (blocking)**. The `workspace.inspect` operation with `--id <id>` re-reads a prepared or resumed workspace (ownership + live-Git checks) idempotently.

**Results-artifact ending.** When the `context.implementation` bundle reports `deliverable: results-artifact`, **read [`references/results-artifact.md`](references/results-artifact.md) now (blocking)** and follow it instead of the rest of Step 4 and Steps 5–7 — it skips `workspace.commit-spec`. A `deliverable` that is neither `pr` nor `results-artifact` ends the run `halted`. Selection, claim, reconcile, and `workspace.prepare` are unchanged.

the metadata branch only receives bookkeeping commits — it NEVER determines where code branches start; the feature branch is cut from the resolved effective base (`origin/<integration_branch>` in the ordinary case).

**Preparation (parent).** The reconciled **spec is read from the metadata working tree**. The `repository.prepare` operation runs at startup, after a dispatched agent writes the change, once after a `contended` write, and on a contended claim. Typed reads fetch on their own, and plain-file reads of the metadata checkout follow every docket write, so no other re-sync is needed. Then run the `workspace.commit-spec` operation with `--id <id>`: it commits the spec copy as the branch's first commit; a `spec-path-occupied` or `workspace-not-ready` refusal halts. Confirm the worktree is clean and record its HEAD as the **pre-dispatch HEAD**. Resolve nothing new: learnings enablement and every repo path come from the startup-check prepared context.

**Verification (parent).** The returned path is a **claim, not proof**. Re-sync the metadata worktree (the `repository.prepare` operation), then verify from git on the metadata branch that `plan:` equals the returned path, the file exists at the metadata tip under `docs/superpowers/plans/` with a backlink to this change, and that the feature worktree is clean with HEAD equal to the pre-dispatch HEAD. On a malformed return, a missing or mismatched `plan:`, a missing file or backlink, a dirty worktree, or a moved HEAD: **halt** (`## Run halted` + the `halted` disposition) — **never adopt**, repair, or commit the child's output, and never retry with the parent or a weaker model. The attach refuses an unsafe path, an unbalanced backlink, an unresolved placeholder, a `plan:` naming another path (`artifact-path-mismatch`), or a path holding another change's file (`artifact-path-occupied`), writing nothing; a lost-response retry with the same bytes replays its applied receipt.

**Continue.** After the dispatch returns, a `PLAN_PATH` return MUST be verified; the child's attach moved the record, so every later write looks its revision up again (*Revision lookups*, Step 2); then the parent MUST proceed into Step 5 — `PLAN_PATH` is a sub-step receipt, **never** a terminal disposition, and neither the child's return nor Step 4's postcondition may be reported as `advanced`. **Dispatch fallback (`halt`):** plan-writer dispatch unavailable — established only per the convention's *Dispatch-capability resolution*, never from a tool name — is **`halt`**: the change stays `in-progress` with the halt reason recorded. Build workers and reviewers read the plan from the metadata worktree (`<metadata_worktree_path>/<plan path>`); the archive transaction retargets every metadata backlink in its own commit.

### Step 5 — Build

The build role — `docket-build` — is invoked **DIRECTED to:** execute the plan task-by-task and stop at the executed plan, carrying the prepare context's `visibility` so every worker payload names its `Visibility`. `docket-build` is a skill to invoke, never a same-name agent to dispatch (convention, *Skill layer*): the invoked skill directs the controller to dispatch one named build-tier worker per plan task and gates on one full-suite run. A rejected attempt to dispatch a same-name `docket-build` agent is the wrong operation, never capability evidence — resume at the skill invocation; no metadata or worktree state changed because that probe was refused. **Proceed through the build — the deliverable is the executed plan, never the decision about how to execute it.** Separately, and without ever relaxing the first: answer any choice it poses from resolved config, surface none, and log one line naming the role and skill if you suppressed a hand-off. Emitting that log line discharges the suppression obligation only; the step is not complete until its git-state postcondition holds — see *Step postconditions*. When `docket-build` cannot be invoked, apply the convention's missing-skill rule: execute the plan inline on the feature branch, warning prominently — the artifact is the executed plan. If the invoked skill's **required nested dispatch** — a build-tier worker — is unavailable (established only per the convention's *Dispatch-capability resolution* — never from a tool name), the build role is **`halt`**: the change stays `in-progress` with the halt reason recorded. When the build role returns `halted`, the `## Run halted` report carries its halt report's gate evidence verbatim, a `tree-survives` finding included — information for the human, never a different disposition.

### Step 6 — Review + ADRs

**Validate the build evidence.** Read the build-evidence record step 5's gate emitted — it must be present, its `head_sha` equal to the branch HEAD, and its `result` either `green` or `skipped` (the repo set `build.gate: off`, carrying `reason: build-gate-off`, no command). Missing, malformed, or stale is a build-contract violation — never review an uncertified branch. Re-mint once yourself: under `build.gate: off`, the `evidence.record` operation with `--id <id> --head <feature head>` and no run dir mints the skipped record; under a local gate, **drive** the native gate — never author a launch/observe/sleep sequence of your own: the `gate.drive.start` operation with `--repo-dir <absolute-feature-worktree> --run-root <absolute-run-root> --owner build --change-id <id> --run-context <token> --json` (`--owner build` resolves the build-owned command; no suite argv; `--change-id` always, so the attempt is charged and the run tracker can find the drive; `--run-context` carries your dispatch prompt's value, omitted only when it carried none) — capture that first JSON response into `gate_reply` and the drive id and owner generation from it, its exit code (if needed) into `gate_rc`, never a zsh read-only special parameter such as `status` (the shared JSON-capture requirement; human text omits the generation) — then the `gate.drive.advance` operation with `--drive-id <id> --owner-gen <gen>` — one slice per call — under docket-build's bounded gate-run posture until a terminal disposition. The typed disposition vocabulary lives in `docket-build`'s `references/gate-driver.md`; only a **`PASSED`** disposition at the current head exposes the raw run dir that feeds the recording below — `FAILED`/`HALTED`/`WAITING` never do.

**Create the durable evidence.** Under a local gate, only from a **`PASSED`** drive disposition whose head equals the current feature head: the `evidence.record` operation with `--id <id> --run <absolute run-dir> --head <feature head>` reads the outcome from the run directory that disposition exposed and the gate command from the build configuration (`build.test_command`) — **no agent-supplied `passed` boolean** — and returns the immutable typed record; a `FAILED`/`HALTED`/`WAITING` or head-mismatched drive produces none. Write the receipt's `block` field to a file: that file is the `--evidence` input for `pr.publish` and `change.mark-implemented`, which each re-verify it against the head. Any review fix below changes HEAD and **invalidates this evidence** — repeat the record step before publishing.

For the `docket-review` role, **select the review tier** deterministically from the build record — take the **highest tier any task routed or escalated to** (an escalation counts as the tier escalated *to*), then map `economy` to `docket-review-lean`, `standard` to `docket-review-standard`, and `premium` or `max` to `docket-review-deep`. When the build emits **no build record** (for example, it ran inline under the missing-skill rule), the tier defaults to `docket-review-standard`, matching the uncertainty sink `standard` is in docket-build's own routing. One modifier: a whole-branch diff of more than **1500 changed lines** — insertions + deletions from `git diff --shortstat <effective base>...HEAD`, the bundle's `effective_base` (`origin/<integration_branch>`, or the parent's branch for a stacked change — the base `workspace.prepare` cut from) — bumps the tier one step, capped at deep — the only selection signal independent of the build's own self-assessment. Log the chosen tier and its reason as one line. Selection is a rule over the build record, never model judgment.

The review role — `docket-review` — is invoked **DIRECTED to:** review the whole branch against its base and return its findings, then stop, answering any choice it poses from resolved config and never surfacing one — log one line naming the role and skill if you suppressed a hand-off. `docket-review` is a skill, never a same-name agent to dispatch, and the skill itself dispatches nothing: you — the controller — dispatch the selected tier wrapper — `docket-review-lean`, `docket-review-standard`, or `docket-review-deep` — foreground, and that wrapper preloads the `docket-review` skill. Its dispatch payload contains:
Feature worktree: <absolute canonical feature-worktree root>
It also contains the branch and base ref, change title and scope, relevant learnings hooks, the evidence record, and the resolved `build.gate` value (from the startup-check prepared context's `build` block). When the `docket-review` skill is missing, apply the convention's missing-skill rule: review the whole branch inline before the PR opens, warning prominently, and dispatch no reviewer. Re-read the learnings index `<changes_dir>/learnings/README.md` first and pull the findings relevant to what this change touched (skipped entirely when `learnings.enabled` is `false`). For any non-obvious decision made during implementation, **dispatch the `docket-adr` subagent** (foreground, at the model/effort its wrapper resolves) — once per decision. Each payload passes the producing change as `{id, path, revision}` (path from the bundle, revision from *Revision lookups*, Step 2); `docket-adr` passes it through as the request's `change`, so `adr.record` assigns the number, updates the index, appends it to `adrs:`, and re-renders `## Artifacts` in one metadata commit, then **returns the number**. Several ADRs go one at a time, each with a fresh lookup. After each returns, re-sync once (the `repository.prepare` operation) and check from git that the number is in `adrs:`. A `contended` from `adr.record`: re-sync, look the revision up again, and re-dispatch once; a second `contended` is a hard error that ends the run `halted`. Review findings that are distinct follow-up work — not this change's own fixes — are **reported as follow-up work in the final report**; nothing is minted automatically, and a human captures reported work deliberately with `docket change create`. On unavailable dispatch — established only per the convention's *Dispatch-capability resolution*, never from a tool name, and never from a rejected same-name role-agent attempt — an undispatchable review tier makes the review role **`halt`** on the same terms as step 5; the `docket-adr` dispatch falls back **`inline`**, with its git-state contract unchanged.
<!-- docket:feature-dispatch:end -->

**Triage the returned findings, then FIX them in-branch.** Findings are repaired on the open branch before the PR opens — a bounded **fix pass**, not a stub for every one. `review.min_fix_severity` (read through the `diagnostic.config` operation; `minor` by default) is the lowest severity that enters it, and blockers are fixed regardless of it. Routing is by the fix's CHARACTER via the shared rubric, never by its severity, and never reaches the `max` tier; every fix runs the `docket-build-task` contract. Before dispatching the first fix task, **read `references/fix-pass.md` now (blocking)** — it owns the routing table, the non-blocker task cap, the per-finding and batched task shapes, the revert-and-record suite gate (bounded at two runs; still-red halts), and the PR-body disposition table. The reviewer's `unverified-build-state` blocker is the one exception you resolve yourself, by re-running the suite — or, under `build.gate: off`, by re-minting the skipped record. A finding that is genuinely distinct beyond-the-branch work is reported as follow-up work in the final report, carrying the backlog verdict final consolidation attaches; a finding about this branch's own diff never is. There is **no re-review** round after fixes — remediation is carried by the worker's own self-review, the suite re-run, and the human reading every fix in the PR diff.

### Step 6.5 — Results (required)

The results artifact is **required for every implemented change** — there is no skip and no close-out condition to weigh. Author `<results_dir>/<YYYY-MM-DD>-<slug>-results.md` from `results-template.md` in a scratch file outside both worktrees; it is written on the metadata branch, never the feature branch. The path is chosen **once per change and reused on every resume** even when the authoring date has since changed (a changed date never mints a second file). Immediately after the H1 title, a **`**Human action:**` statement** says whether human action is needed — during implementation it may say the assessment is pending, but final results give a settled assessment consistent with the rest of the artifact, and the implemented boundary refuses a missing or empty statement. `## Outcome` is required; every other section is **conditional** — omit an empty heading and its subsections rather than filling it, and never write a `None`/`N/A`/`not applicable` body (whole-section filler refuses at the implemented boundary). The `docket:backlink` block above the title is owned by the `change.attach-results` operation — never hand-author its markers.

**Human actions and testing** labels every item **Important** or **Optional**, written for a mid-level engineer with little knowledge of Docket internals. An **Important** item marks a meaningful verification gap or necessary human judgment (never a new automated merge requirement) — give the reason, when the action matters, and what remains uncertain if skipped. An Optional walkthrough MAY exercise behavior automated tests already cover — a routine suite rerun is not a functional walkthrough. Every item carries prerequisites and setup, concrete steps with observable expected results, and cleanup when it changes persistent state — complete enough to run without reconstructing missing commands. Do not infer coverage from a green suite: inspect the relevant tests and evidence, and where coverage is genuinely uncertain report that uncertainty under Known issues and follow-ups or Verification performed rather than authoring a speculative checklist. The section holds only what a human should do or check — never a record of what the run already checked, which belongs under Verification performed.

**Checkpoint lifecycle.** The coordinator captures the findings it already knows at each evaluated boundary: **(i)** after the build role returns; **(ii)** after review returns, and again after fixes with their **actual** dispositions; **(iii)** before a planned pause, halt, or handoff, but **only** when the ownership and gate-drive contracts permit a safe write; **(iv)** at final consolidation, before the implemented transition. A checkpoint is an **evaluated boundary, not a scheduled commit**: unchanged substantive content is a no-op — no empty commits, no per-observation commits, and **never commit or move HEAD beneath a live gate, a running worker, or a transferred drive**.

**Per-checkpoint mechanics** (in order):

1. Verify ownership and quiescence — no live gate, running worker, or transferred drive.
2. Read and **preserve** the prior results content — from `<metadata_worktree_path>/<results path>` when `results:` is set; a checkpoint updates it, never truncates it — except final consolidation, which condenses the review findings (*Review findings* below).
3. Write the update into the scratch file.
4. Attach it: the `change.attach-results` operation with `--id <id> --revision <revision> --path <results path> --markdown <file>`, at a freshly looked-up revision (*Revision lookups*, Step 2), writes the file with its backlink and sets `results:` in one metadata commit that never moves the feature head; later checkpoints keep the **same path**.

**Evidence sequencing.** Results prose is **never gate evidence**, and a results checkpoint never moves HEAD, so it never stales evidence. Obtain gate evidence for the final code head through the gate driver; any code commit (a fix) still invalidates it. **Never** rewrite results solely to paste the final gate's SHA or timestamp. A new material finding surfaced by the final gate is preserved in results, the fix/halt policy applies, and evidence is re-established after any commit.

**Known issues and follow-ups** merges unresolved findings, limitations, and follow-up work into one plain-language section — each entry gives when the problem occurs and what the person experiences, its practical impact, whether it is confirmed or suspected, any workaround, and the suggested next action. Follow-ups recorded there hold out-of-scope work for **human triage** — final consolidation checks each against the backlog and names any match (*Backlog match* below), and the run **never** mints a change, issue, ADR, or learning automatically. An in-scope defect stays fix/block/halt work regardless of where it is written. Final consolidation verifies that no material coordinator handoff remains only in chat, and the final report links the durable results file.

**Backlog match.** Once, at checkpoint (iv) final consolidation, after the Known-issues entries are settled, match each out-of-scope follow-up against the backlog; an in-scope limitation or a verification-coverage note gets no verdict, and earlier checkpoints never run the match. Run the `status` operation (argv from the capability catalog) with `--json` and keep the changes whose `status` is `proposed` or `deferred`, excluding this change — claimed, built, and archived changes are never candidates. For **every** candidate, not only those with similar titles, read the `## Why` and `## What changes` sections of the record at its `path` in the metadata working tree, and its linked spec only when those leave the match undecided. Give each follow-up exactly one verdict: **Fits #N** — #N's stated scope covers it, or would with a small extension that does not change what #N is for (name the closest; mention any others); **Related to #N** — same area, but folding it in would change what #N is for; or **No existing change fits (checked K)**, K being the number of proposed and deferred changes checked. End the entry's suggested next action with the verdict and the action for #N's state: a needs-grooming `proposed` #N — edit it through `docket-groom-next <N>` (`change.groom` `revise`), and it stays needs-grooming; a groomed `proposed` #N — edit it through `docket-groom-next <N>` (revise), which also revises its spec when needed; a `deferred` #N — revive it (`change.revive`), then edit it as a proposed change, weighing whether the follow-up strengthens the case to revive; related or no fit — a new change a human captures (Step 3), linking any related #N under `related:`. The final report's follow-up list carries the same verdict per item. The match only recommends: it never edits, creates, revives, defers, or kills any change, writes only this run's results file and final report, and is never a gate. If the `status` read fails or a candidate record cannot be read, write the entries without verdicts and add one line to `## Verification performed` saying the backlog check did not run, naming any unreadable candidates — never halt, retry in a loop, or block the implemented transition on it.

**Review findings.** The PR body is the full review disposition table's home (`references/fix-pass.md`). Checkpoint (ii) persists the returned findings — in full detail if useful — so they survive a halt before the PR exists; final consolidation condenses them. `## Verification performed` then carries one line naming which review ran (the tier, or an inline review) and how its findings ended, with no PR number — the PR does not exist yet. `## Known issues and follow-ups` carries an entry for every finding not fixed (`deferred`, `reverted`, or `recorded`) and every `reported` beyond-the-branch finding, plus any fixed finding that still explains a remaining risk or a consequential design decision. A fixed finding with no remaining risk appears in final results only through that summary line.

**Ownership.** The coordinator authors and consolidates the artifact. A controller executing the invoked build role MAY perform the **build checkpoint** on the coordinator's behalf under the explicit caller contract; task workers and reviewers **never** independently edit the file; there are **no concurrent writers**. Results are never evidence that the head passed the gate.

### Step 7 — PR + stop

**Publish the feature head.** The `workspace.publish` operation with `--id <id> --head <feature head>` inspects the owned workspace and pushes the exact head through the landed non-forcing publication, returning the verified remote head. It refuses when the reinspected head differs from `--head`; a divergent remote ref is `contended`, unknown post-effect state is `unknown` (reprobe on retry) — neither forces, and no PR opens here.

**PR-body assembly.** The PR body carries no build-evidence block. In a private repository the authored title and body follow the private-repository writing rule: no `#<issue>` reference, no change id in the title, and `pr.publish` publishes the body verbatim, with no back-link line and no links block.

**Best-effort PR→issue reference.** If the change carries an `issue:` value, add a plain `#<issue>` reference to the PR body — but **never `Closes #N`**, so merging the PR never auto-closes the referenced issue. Skip silently when `issue:` is unset — the reference is a one-time courtesy, not a build gate.

**PR-body back-link.** `pr.publish` renders and upserts a **back-link line** pointing home to the change on the metadata branch — a first body line of the shape `↩ Change <padded-id> — <title>` linking to the change file on `docket` (built with the same blob-or-bare-path logic) — plus a Docket-owned links block pointing at the plan and results files on the metadata branch; never author either in the body.

**Review outcome.** The authored body names the reviewing tier and carries the **findings disposition table**: one row per finding, marked fixed (with its commit SHA), deferred, reverted, recorded, or reported — the states `references/fix-pass.md` defines.

**Publish the PR.** With the authored title+body and the Step 6 evidence file (the `evidence.record` receipt's `block` text) each in a request file, the `pr.publish` operation with `--id <id> --head <feature head> --body <request-file> --evidence <evidence request-file>` reparses the evidence (never a prior result) and verifies local HEAD == published remote head == evidence head == requested head, and that the feature branch, effective-base branch, and repository identity agree, BEFORE calling the landed GitHub adapter; it then inserts or replaces ONLY the Docket-owned backlink and plan/results links blocks (authored prose byte-preserved) and returns the canonical PR reference, URL, number, head, base, and disposition. `unknown` stays `unknown` — reprobe, never a duplicate PR — and the result redacts the body bytes. It refuses `record-invalid` (`invalid-state`) before any GitHub call when the change, a `depends_on` target, or a stack ancestor carries a validation error (associative links are never checked): no PR was created or edited — repair exactly the records the result's `findings` name, then re-publish; the run keeps its existing halt posture for a typed refusal.

**Leak check (private repositories).** `workspace.publish` and `pr.publish` refuse `leak-detected` (`blocked`) when anything they would expose carries a docket fingerprint; the result's `leaks` list names each hit (source, commit, file, line, rule, matched text). Nothing was pushed or opened. End the run `halted`: write the hit list into the `change.halt` report — never reword, amend, rebase, or force-push to get past it, and never retry. `leak-check-unverified` (`external-failed`) means the check could not run; treat it as any external failure. `metadata-on-shared-remote` warnings go in the run report only.

**Mark implemented.** The `change.mark-implemented` operation with `--id <id> --revision <revision> --head <feature head> --pr <reference> --evidence <evidence request-file>` is the final mutation in this scope. Before its transaction it reprobes Git and GitHub and proves: the change is still the exact `in-progress` revision, `reconciled: true`, linked to the verified plan; local and remote feature heads equal the supplied head; valid evidence names that head and a passed gate; exactly one verified PR for the feature branch targets the resolved effective-base branch and names that head; and a results artifact is attached, read from the metadata branch, and satisfies the final content contract and its artifact identity (missing, invalid, or unattached results refuse the transition). It then applies the landed transition atomically — `status: implemented` + `pr:` + updated date + the verified evidence as the record's `## Build evidence` section + `## Artifacts` block + inline board + audit receipt (letting the sweep read `pr:`), rendering the board inside that transaction, so no separate Board pass runs. It does NOT clear the claim, delete the branch/workspace, merge, archive, or close descendants. A retry against an already-`implemented` change with matching PR/head returns the prior applied outcome, never a duplicate transition.

**Verify the run.** The `run.verify` operation with `--id <id>` is read-only: it reports one closed verdict — `run-complete` / `run-unclaimed` / `run-incomplete` / `run-halted` / `run-waiting` — and enumerates every unmet condition with its stable reason and observed identity. Automation keys on the typed verdict, **never** the exit code (all verdicts exit 0). `run-complete` is the receipt that Step 7's postcondition (or the results-artifact ending's) holds; `run-halted` is the closed verdict for a change carrying a `## Run halted` marker — a human is needed, and an attributed caller re-dispatches it through the resume path (the `change.resume-halted` operation with `--acknowledge-quiescent`, Step 2), never a fresh claim. `run-waiting <change-id> <handoff-id> <phase>` is the closed verdict for a change whose gate stopped at a safe, resumable continuation — neither complete nor failed: an attributed caller resumes that exact handoff rather than drawing another change or re-dispatching a fresh run, and precedence is completed-run postconditions first, then a valid `run-waiting`, then ordinary `run-incomplete`; a persisted `run-halted` stays terminal. A run **dispatched with an explicit change id, continuation id, and run key resumes, not restarts**: its FIRST act is the `run.continue` operation with `<key> <continuation-id>`, claiming the recovered drive **before any other work**; it never launches a replacement test, and this is a **continuation, not `run-retry-once`** — the key stays active until a true terminal disposition. Each `run-retry-once` authorizes exactly one next dispatch; the run tracker may grant another on a later eligible attempt while the configured `run.max_attempts` budget allows, and a continuation consumes none of that budget. A gated parent's prompt may also carry a **run context** token; pass it, always as `--run-context`, into every build-owned `gate.drive.start` (`--owner build` — Step 6's evidence re-mint and re-gates, the build role's final suite gate, and each post-repair attempt the build role starts) this run performs — each invoked with `--json` per the shared capture requirement and each always carrying `--change-id <id>` — and into the Step-2 claim, omitting it only when the prompt carried none (a `run-untracked` or ungated run). Build-task workers never receive it: they run their tests directly and call no gate operation.

**STOP.** The change stays in `active/` as `implemented` until a human merges it, or approves `docket-finalize-change` to merge it.

### Step postconditions

Each step below is complete only when its row holds — read from **git**, never from a sub-skill's report or its own narration. One qualification: the build-evidence record of rows 5–6 is an in-context artifact, not a git object, so only its `head_sha` == HEAD condition is a git fact — load-bearing, not decorative. The conditions are **cumulative**: each holds in addition to every earlier step's, each read **as of the close of its own step**. These certify a **step**, never the run. **Once a change is claimed, and absent a `halted` disposition or a Step-3 kill, the only postconditions that also complete the run are Step 7's and the results-artifact ending's** — a satisfied intermediate row is never licence to stop. A run that ends any other way ends on a **disposition**, not on a postcondition.

| Step | Complete only when |
|---|---|
| 2 Claim | `status: in-progress` + `branch:` + `updated:` committed on the metadata branch **and landed** (an `applied` claim receipt). |
| 3 Reconcile | `reconciled: true` and a dated `## Reconcile log` entry landed on the metadata branch — or, on the kill path, the change archived. |
| 4 Worktree + plan | the spec copy committed as the first commit on `<type>/<slug>`, then `plan:` and the plan file with its backlink landed on the metadata branch, the feature HEAD unchanged by planning. |
| 5 Build | the executed plan committed on `<type>/<slug>`, with a build-evidence record at `result: green` (or `skipped` / `build-gate-off` under `build.gate: off`) whose `head_sha` **equals branch HEAD**. |
| 6 Review + ADRs | that record still present at `head_sha` == HEAD **after** any fix commits, and every ADR the run produced landed in `adrs:`. Known-weak row: on a clean review this reduces to Step 5's, because whether a reviewer ran is not a fact about git. |
| 7 PR + stop | the branch pushed (`origin/<type>/<slug>` resolves), the PR open, and `status: implemented` + `pr:` landed on the metadata branch; `results:` set and the final results file with its backlink on the metadata branch, and the record's `## Build evidence` section naming the PR head. |
| Results-artifact ending | the change `done` and archived on the metadata branch, `results:` set, and the final results file with its backlink on the metadata branch. |

Rows 3, 4, 6 and 7 each carry, in addition, the **field-write rule**'s link-bearing condition on every metadata commit they name: the regenerated `## Artifacts` block in the same commit.

Steps 0, 1 and 6.5 get no row: 0 produces nothing scoped to this change, 1 is a pure read, and 6.5's artifact is certified by Step 7's results condition or the results-artifact ending's.

### Terminal disposition (driver contract)

Every run ends by declaring exactly **one** of four dispositions, so any driver keys on the outcome instead of parsing prose:

| Disposition | Meaning | Driver action |
|---|---|---|
| `advanced` | Built a change → PR opened (Step 7 reached), or completed a results-artifact change (done and archived, with a valid results artifact attached). | continue |
| `contended` | Selected a change but lost the conflict-checked claim (Step 2); **nothing built**. | continue — re-select next |
| `drained` | No build-ready+claimable change in scope (Step 1's empty queue). | **stop** |
| `halted` | Stopped needing a human — fundamentally-invalidated design (Step 3) or a hard error. Recorded on the metadata branch as a `## Run halted` section through the `change.halt` operation — see Step 3 for the write; the `run.verify` operation reads it back as the `run-halted` verdict. | **stop + surface** — except a tracked loop whose verdict is `run-next`, which continues |

The driver's rule: **continue on `advanced`/`contended`, stop on `drained`/`halted`** — except that a tracked loop continues past `halted` when the run tracker's verdict is `run-next` (a halt on a change picked from the queue, still under `run.max_consecutive_halts`); an untracked driver has no verdict and stops on every `halted`. The contract is **driver-agnostic** — it names run outcomes, not any one driver's mechanics; `/loop` is *recommended*, not required (see the README drain-pattern doc).

**The obligation is on the agent, not only the driver** — the run does not end until exactly one of
the four is declared. A final report that declares a step-scoped or invented disposition — a build
disposition, a review outcome, "complete" — is by construction an aborted run, whatever else it
reports. `advanced` is claimable only when **Step 7's postcondition** or the **results-artifact
ending's** holds — stated in *Step postconditions* above, not here.

The final report **enumerates** what happened: the change built (if any), each change **skipped with its reason** (needs-grooming / on hold / already `in-progress` / waiting on an unmerged `depends_on` / outside the id allowlist), any follow-up work **reported for deliberate capture**, each with its backlog verdict when final consolidation produced one (Step 6.5 *Backlog match*), and which disposition ended the run.

### Atomic board rendering

Every status-writing transaction in this skill — the `change.claim`, `change.reconcile`, `change.mark-implemented` operations, and the reconcile-kill's `change.kill` operation — renders the inline board **atomically inside its own metadata commit**, so this skill runs **no** separate Board pass and never hand-renders the board. The reconcile-kill path is no exception: the `change.kill` operation archives the killed record and renders the board in one transaction, so the board drops the killed change without any follow-up commit. The build's correctness rests on the conflict-checked change-file write, not the board.

## The reconcile pass and the `reconciled` flag

A change is drafted against a *snapshot* of the codebase, ADRs, and other in-flight changes; reconcile is the antidote, run at the **last responsible moment**: after claim (the change is ours) but before planning (nothing is committed to yet).

`reconciled: false` at birth; set to `true` only after the reconcile pass completes and commits. It is **(1) an audit signal** — paired with the dated `## Reconcile log` entry, it proves the change was freshened against current reality; **(2) a resume-safety guard** — on any resume of an `in-progress` change, **read `references/edge-paths.md` now (blocking)** for the resume rules.

`reconciled` is **NOT a selection criterion** — build-readiness is `spec:` plus satisfied `depends_on`; a change sitting at `reconciled: false` is still build-ready, and reconcile happens in step 3, after selection and claim.

## Branch & metadata discipline

### The field-write rule

Every change-file field write in this run (claim's `status:`/`branch:`, reconcile, `plan:`, `adrs:`, `results:`, `pr:` + `status: implemented`) lands through a **`change.*` / attach / mark-implemented transaction** in the metadata worktree on the metadata branch — never a hand-edit, never in the feature worktree — which reloads fresh origin, checks the exact record revision, and commits and pushes atomically. The skill **never invokes a facade renderer and never hand-writes a derived view**: for any **link-bearing field** (`spec:`/`plan:`/`adrs:`/`pr:`/`results:`), the transaction regenerates the `## Artifacts` block and inline board in the same commit. The halt-path authored sections also land through transactions, never a hand-edit: the `change.halt` operation writes the `## Run halted` section (Step 3) and the `change.resume-halted` operation removes it on resume (Step 2), each an exact-revision transaction that renders the inline board in its own commit. The skill authors the halt report as a request file and hands it across; it never edits the section bytes itself. **Stage by explicit path** — that tree is shared, so a bare `add -A` commits another agent's staged work under your message.

### Feature branch invariants

New change ⇒ the `workspace.prepare` operation with `--id <id> --revision <revision>`, which cuts `<type>/<slug>` from the resolved effective base — `origin/<integration_branch>` in the ordinary case, except for a change carrying `stacked_on:`, whose base is the parent's effective base per the convention's *Branch model* exception and its stacked-changes reference. The workspace is prepared AFTER claim + reconcile, adds only the spec copy + code, and **never modifies** docket metadata (the change file, `BOARD.md`, ADRs) — at merge, the 3-way merge takes the integration branch's side for the change file unconditionally, so there is no conflict and no revert needed. (The change file may not even exist on `origin/<integration_branch>`.)

Metadata commits (per the **field-write rule**) happen in the metadata working tree; only code commits happen in the **feature worktree** on `<type>/<slug>` — the plan and results files and their fields are metadata writes through their attach transactions, and build evidence lands in the change record. Never cross these streams — a metadata write landing in the feature worktree silently diverges or conflicts at merge. (The single deliberate cross-tree write is `workspace.commit-spec`'s spec copy, an operation-owned commit.)

This skill is safe to invoke from any branch: it `git fetch`es and operates against `origin/<integration_branch>` and the metadata branch explicitly; the branch the human happened to be on when they typed the command is irrelevant.
