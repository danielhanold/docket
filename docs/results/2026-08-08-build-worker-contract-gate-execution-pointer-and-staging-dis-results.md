# Build-worker contract: gate-execution pointer and staging discipline — results
Change: #0249 · Branch: feat/build-worker-contract-gate-execution-pointer-and-staging-dis · PR: (see change file `pr:`) · Plan: docs/superpowers/plans/2026-08-08-build-worker-contract-gate-execution-pointer-and-staging-dis.md · ADRs: none

## Verify (human)

- [ ] Read the two new clauses in `skills/docket-build-task/SKILL.md` as a **worker would**, not as their author. They are contract prose whose only consumer is a dispatched model, so the merge-gate question no test can reach is whether they are unambiguous at the moment of action: does a worker whose focused verification is about to outrun a foreground call know exactly what to do, and does a worker about to `git add` know exactly which paths are its own? The guards pin that the clauses are present and bound to their claims; they cannot pin that the clauses are followable.

## Findings

**The whole-branch review returned six findings, zero blockers; all six were fixed in-branch.** Their dispositions are in the PR body's table. Three are worth recording beyond that, because each names a defect class rather than a slip:

1. **A new normative clause needs a landing in the outcome vocabulary** (finding 1). The fail-closed clause told a worker what *not* to claim — never infer success from an unfinished run — without naming what to return instead. None of `COMPLETE`, `NEEDS_ESCALATION`, or `BLOCKED` fits an unverified run on its face, and the controller reads a reasonless `NEEDS_ESCALATION` as a malformed return that halts the build. So the most likely worker response to a correctly-written prohibition was a malformed return. Fixed by naming `BLOCKED` in the clause itself (commit `0f7ad4c8`) rather than extending the `## Outcomes` enumeration: the rule has to bind at the moment the worker stops observing, which is where it is read. **The generalization:** a prohibition added to a contract that has a closed return vocabulary is incomplete until it says which return it maps to.

2. **A generic contract acquired a repo-specific claim** (finding 2). The pointer paragraph shipped with the aside `on this repo, often the full suite` — the only such phrase anywhere under `skills/`. This body is distributed into consuming repos and itself declares that repository instructions override it, so the aside was false or meaningless everywhere but here. It also contradicted step 4 of the same section (`Focused, not the whole suite`) with no reconciling sentence, on precisely the question the paragraph exists to settle. Fixed by dropping the aside and scoping the paragraph to a long-running *focused* verification (`449a7a9c`), which leaves step 4's rule untouched. **The generalization:** when authoring inside a skill body, the reader is a worker in an unknown repo — a sentence that is only true here is a defect even when it is locally accurate.

3. **Two of the three parts of a critic-widened clause were guarded; the third was not** (finding 3). Spec assumption A1 records that the inline consequence was widened at the auto-groom critic gate from never-yield alone to never-yield **+ finite observation +** fail-closed, precisely because "observe by blocking" without a bound converts a measured yield-and-stall failure into an unbounded silent block. The guard block pinned never-yield and fail-closed. Deleting `keep the observation **finite**` would have reinstated the exact hazard the critic gate existed to prevent, with every change-0249 assert still green. Fixed by one more single-gap assert (`a7f64d20`), mutation-proven to be the only assert that reddens on that deletion. **The generalization:** when a clause is widened during design, the guard must be re-derived from the widened clause — guarding the original shape leaves the added part free.

**Plan deviation (deliberate, reviewed, and confirmed sound).** The plan's Task 1 Step 4 directed placing the new staging bullet *after* the escalated-worker bullet. The builder placed it *before*, because `tests/test_inline_role_stop_scoping.sh` (change 0212) anchors a `WINDOW=6` proximity guard on the **last** bullet of the Scope prohibitions block and requires both halves of the two-sided scoping clause within six lines after that anchor; appending pushed the clause ~9 lines out of the window and reddened two asserts in a test file outside this change's three-file boundary. Placement was therefore the only available fix. The reviewer assessed the resulting prose and confirmed the carve-out sentence is self-contained — it re-opens its own escalation condition rather than leaning on an antecedent, and `taking the same leave-and-report posture` resolves *backward* within the same bullet — so spec A4's adjacency requirement still holds. The residual cosmetic cost (the escalation condition opening twice in consecutive bullets) was review finding 5 and is fixed in `d168a03b`. **Worth knowing for the next edit to this file:** the Scope prohibitions block is now constrained at both ends — 0231's phrase pins inside it, 0212's proximity window after it — so a bullet cannot simply be appended there.

**Mutation-testing hazard specific to this file.** The Scope bullets are hard-wrapped, so several guarded phrases (`adding another commit, never by amending`, `You may revise or replace them`) span a line break. A literal `perl -0pi` substitution against them silently no-ops, which is indistinguishable from a guard that correctly survived the mutation — a false proof of robustness. Every mutation in this build was confirmed with a `grep -c` before/after taken through a whitespace-flattened copy, and the fix workers used `\s+` between words. This is the learnings finding `phrase-grep-over-wrapped-prose` recurring in the verification step for the fourth recorded time (#218, #231, #224, now #249); it is a candidate for the harvest to promote, since the mitigation clearly belongs in the probe template rather than in each author's care.

**Size-budget trajectory.** `skills/docket-build-task/SKILL.md` went 122/1087 → 139/1330 over the build, against a row raised once, in-diff, from `130 1150` to `145 1350`. Five of the six fix commits touched that file or its guards and none needed a second raise, but headroom is now roughly 6 lines / 20 words. The next edit to this contract will almost certainly force the row up again.

## Follow-ups

**The detached-gate bash resolution hazard — already filed as change #0150, not minted again.** Every worker in this build hit the same trap: `scripts/run-tests.sh` sets `TEST_BASH="${DOCKET_BASH_PATH:-$(command -v bash)}"`, and launching the suite detached through a login shell yields a PATH without Homebrew, so `command -v bash` resolves to macOS bash 3.2. The run then reports ~14 unrelated files failing on `mapfile: command not found`, each 6–7× over its wall-clock budget — a large, confident, entirely spurious red that reads as a genuine regression. Every one of those files passes individually, and the suite is 88/88 green once `DOCKET_BASH_PATH=/opt/homebrew/bin/bash` is exported into the detached environment.

This is squarely inside change #0150's scope ("Pin or report the resolved shell toolchain across the test suite"), whose spec has already settled **report, never pin** — a runner that reported its resolved `bash` would have made this self-diagnosing on the first line of output instead of costing each worker a debugging detour. No stub was minted; #0150 is the home. Two concrete inputs for whoever builds it, from four independent hits in one build:

- The report must name the resolved **bash**, not only `grep`. The 0130 story that motivated #0150 was about `grep`, but the failure that actually recurs here is `bash`, and it is louder: a wrong `grep` silently passes, a wrong `bash` produces a mass false red.
- The gate's **detached launch shape** is where the degradation is introduced, and `skills/docket-build/references/gate-execution.md` — which specifies that launch shape — says nothing about propagating the toolchain into the new session. Whether the mitigation lands in the runner (report), the reference (propagate), or both is #0150's call, but the detached-launch case is the one that bites and it should be named in its design.
