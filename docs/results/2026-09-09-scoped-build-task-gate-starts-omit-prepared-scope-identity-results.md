# Scoped build-task gate starts omit prepared scope identity — Results

## Outcome

The maintained build-task caller contract now hands every scoped task-owned `gate.drive.start` the
complete identity bundle its recovery scope pinned, closing the omission that made the driver reject
every scoped worker's focused gate before its first test (the failure that halted change 0323).

Three maintained markdown surfaces were fixed, and their embedded mirrors regenerated:

- `skills/docket-build-task/SKILL.md` — the worker now starts its task-owned drive from the canonical
  feature worktree and passes `--repo-dir --change-id --task-id --phase build --branch --scope-id
  --child-cap --gate-context` (when a dispatch context is present) alongside the existing
  `--owner task --run-root --json`, unchanged from what `prepare-scope` pinned.
- `skills/docket-build/SKILL.md` — the controller's feature-dispatch payload now hands the worker one
  complete start-ready scope bundle (change id, task id, phase, branch, scope id, child capability,
  and dispatch context when present); the parent capability stays parent-only and never enters a
  worker prompt.
- `skills/docket-build/references/gate-caller-loop.md` — the `start` operation row documents the
  identity flags a scope-bound start must carry and that the driver rejects a start whose identity
  does not match the prepared scope.

No behavior change to the gate driver, `scopeIdentityMatch`, the CLI flag surface, capability/
handoff/takeover/credential-redaction semantics, or the invalid-request error vocabulary — the CLI
already accepted every flag; the defect was a mechanically incomplete caller contract. The two
existing embedded-mirror surfaces are regenerated so source and generated bytes stay aligned; the
"installed" surface is written verbatim from the embed at install time, so the fix covers all three.

A new whole-repository guard, `TestGateDriveScopedStartIdentity`
(`internal/repoguard/gatedrive_scope_identity_test.go`), makes the regression un-reintroducible.

## Findings and limitations

### Guard residual: a scoped start authored without `--owner task` in the same paragraph

Prong A discovers sites by the syntactic co-occurrence of `gate.drive.start` and `--owner task` in one
collapsed paragraph. An author who instructs a task-owned start while omitting the `--owner task` token
from that paragraph would not be classified as a site and would dodge prong A. This residual is
recorded, not hidden, in the guard's header: the driver itself still fails such a start closed at run
time (scope-identity-mismatch), and prongs B and C independently assert the controller payload and the
shared caller-contract prose.

### Single-bind-per-scope observed during the build (out of scope)

A prepared recovery scope binds exactly one drive; a second scoped start against a spent scope returns
invalid-request. This surfaced while the build worker verified the fix but is explicitly out of change
416's scope — the broader concurrent-scope / duplicate-drive behavior is tracked by change 405.
