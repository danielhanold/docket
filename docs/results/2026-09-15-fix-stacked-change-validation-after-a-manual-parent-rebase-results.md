# Fix stacked-change validation after a manual parent rebase — Results

## Outcome

Two independent checks that falsely rejected an otherwise valid stack after a manual parent rebase were corrected, without weakening the protections against genuinely lost child work.

- **Child preservation (`internal/gitcli/preservecommit.go`).** `ProvePreserved` gained a third proof path: when a child's exact delta does not reproduce at the target tip, the proof now also accepts the case where the **complete** `base → source` delta reproduces at **one** commit reachable in `base..target` (new proven kind `PreservationByHistoricContent`, wire value `exact-content-history`). This lets a legitimately rebased child whose exact snapshot survives mid-history stay "included" even when later stacked children evolve the same shared files. The completeness rule is strict — the whole delta must match at a single commit; a proof is never assembled from entries spread across different commits — and the candidate pool is bounded to `base..target`, so history beyond the pinned target (for root closeout, the verified root merge-result commit) can never supply the proof. The tip-only and original-ancestry proofs are unchanged, git observation errors remain errors (never verdicts), and no-common-base / multi-base still refuse. Two supporting helpers were added: `commitRange` (`git rev-list target ^base`, newest-first, typed failures) and `deltaMatchesAt` (the single exact object/mode/deletion comparison now shared by both the tip proof and the fallback, so the two can never diverge on what "exact" means).
- **Ready-workspace validation (`internal/workspace/{inspect,publish,cleanup}.go`).** The three mirrored copies of the ready-phase original-base ancestry gate were removed. A registered, on-ref, tip-matching, clean workspace whose head no longer reaches its recorded creation base is now a legitimate ready state (a manual parent rebase), not `branch-missing` / a publish refusal / a cleanup block. Inspection still computes and records `BaseReached` as a **fact** (it just no longer decides `Kind`); publication verification and cleanup verification drop the gate entirely. Every other check is preserved identically across all three sites: manifest ownership, registration, ref existence, non-detached HEAD, on-feature-ref, `HEAD == ref tip`, clean tree, and non-forcing removal. The **allocating-phase** ancestry gate (an unfinished allocation with a rewritten branch is not safely resumable) is untouched, as is the separate remote fast-forward divergence check in the publish push path.

All app-layer callers (rebase, publish, merge, stacked/root closeout) inherit both corrections through the existing call sites unchanged — they branch on `Outcome != PreservationProven` only, never on `Kind`, so the new kind flows through transparently.

No departures from the spec's minimal algorithm. No new configuration, persistence, rebinding/synchronization command, synthetic merge commit, or merge-policy change was introduced.

## Findings and limitations

### Historic-snapshot fallback walks `base..target` on the not-proven path (minor, by design)

When the child's delta does not reproduce at the target tip, `ProvePreserved` now inspects candidate commits in `base..target`, one git tree read per candidate, until a complete match or exhaustion. This cost is incurred only on the previously-refusing (tip-mismatch) branch, and the range is bounded to the pinned target, so worst-case cost in root closeout is O(children × range) git invocations. Correctness is unaffected. This is inherent to the spec's deliberately minimal algorithm (inspect commits reachable in `B..target`); candidate pruning was judged out of scope for this fix. If profiling later shows it matters, prune candidates before the tree read (e.g. a name-only pre-filter on the delta paths) as a separate change.

### Scope limit (from the spec)

The fallback requires an exact snapshot to survive in reachable history. Arbitrary conflict resolutions or squashes that eliminate every matching snapshot remain unproven — this preserves the existing treatment of historical inclusion, including later explicit reverts. Recovering those is explicitly out of scope.
