## Findings

**The bug and the audit landed exactly as specified.** The reconcile re-ran the spec's §2 audit against `origin/main` and found the snapshot exact: 16 `.docket.yml` occurrences across the same 5 skill files, same distribution, one false claim. No second false claim; no site the spec had not already classified. The spec's §4 fallback (rephrase `docket-convention/SKILL.md`'s "value *read from* the file" sentence) was **not** triggered — read in context it is about where the config file *lives*, and the same file attributes the actual read to the resolver.

**ADR-0052 gained a dated `## Update`** (not a new ADR — the spec was explicit) naming `tests/test_config_read_channel.sh` as the second enforcer and drawing the line between the two: `test_docket_example_yml.sh` guards the **key** side (every documented key is really resolved and exported), the new test guards the **prose** side (no skill body tells an agent to read the file). It was published onto `main` through the ADR-only publish path, since ADR-0052 was already published there.

**The plan's exclusion assert was wrong, and the implementer caught it.** The plan specified a single directory-*prefix* assert (`^file\tskills/docket-convention/`) to prove the two exclusions are skipped. That form also forbids scanning `skills/docket-convention/github-board-mirror.md` — one of the five sites this very change must mark — so it could never have gone green, and it contradicted the guard's own fixture (e). Replaced with two exact-path asserts, one per declared exclusion. The plan text was wrong; the deviation was ruled in before the task review.

**The whole-branch review found a real fail-open in the guard, fixed in this change.** The marker originally admitted the whole **line**, and these skill files are one-paragraph-per-line — so a later edit could add a *new* violating occurrence into an already-marked paragraph and the guard would stay green. Reproduced concretely by the reviewer. Closed by requiring the marker count on a line to **equal** the occurrence count, with two new fixtures (2-occurrence/1-marker rejected, 2-occurrence/2-marker accepted, non-vacuously). The guard's header comment, which had claimed same-line attachment "has no such degree of freedom", was corrected to say what is now true — the freedom moved from position to line content, and the equal-count rule is what closes it.

This is worth reading as a pattern, not an incident: the same-line marker choice below removed one fail-open (attachment) and quietly introduced another (line content). A marker-scoped guard has a fail-open wherever its *unit of admission* is coarser than its *unit of violation*; picking a different unit moves the hole rather than removing it, and only counting closes it.

**Deviation from the spec: the marker is same-line, not own-line.** The spec's *Verification* assumed each of the four markers would occupy its own line and budgeted for it (189→190, 107→109, 17→18 — the last with only 2 lines of headroom). This change appends each marker to the end of the occurrence's own line instead. Two reasons: a position-sensitive attachment rule ("nearest preceding non-blank line") fails open and reads green the moment an edit inserts a blank line, which is failure mode 2 in the `marker-scoped-guard-needs-a-population-floor` learning; and zero new lines removes the mirror file's headroom risk entirely. The spec's stop-point is unchanged — every occurrence carries a declared class marker. Final measurements: 189/193 · 4140/4200 lines·words for `docket-finalize-change/SKILL.md`, 107/118 · 2331/2393 for `docket-status/SKILL.md`, 17/19 · 424/462 for `github-board-mirror.md`. No budget row was raised.

**Deferred minor, correctly deferred:** the guard uses `set -uo pipefail` without `-e`, so a future edit referencing an unset variable would abort the whole script rather than reddening one assert. This is the house convention across all 64 `tests/test_*.sh` files, and `-e` would break the accumulate-then-report assert model. No action.
